## T. Результат и проверка

### Подача результата

- 🟢 Как исполнитель, я хочу подать предложение результата со ссылками на PR / коммит / релиз, статусами критериев задания, выполненными проверками и ограничениями, чтобы результат можно было проверить без переписки.
  - AC:
    - Подать может только исполнитель задачи с ролью member или выше; остальным — `NOT_ASSIGNEE` / `PERMISSION_DENIED`.
    - Предложение относится к текущей версии задания (или версии, закреплённой в сессии); критерий, которого нет в задании, отклоняется (`UNKNOWN_CRITERION`).
    - После подачи состояние результата задачи — «Awaiting review»; назначенный проверяющий получает уведомление.
    - Подача пишется в журнал задачи.

- 🟢 Как исполнитель, я хочу подать новую версию предложения после доработки, не меняя прежнюю, чтобы проверка всегда относилась к конкретной неизменной версии.
  - AC:
    - Содержимое поданной версии изменить нельзя; новая версия получает следующий номер и ссылку на заменяемую.
    - Заменить можно версию на проверке или возвращённую на доработку; заменённая получает статус «Superseded» и больше не проверяется.
    - До проверки автор может отозвать свою версию.

- 🟢 Как агент (служебная учётная запись), я хочу подать предложение результата через REST или MCP по тому же контракту, что и человек, чтобы результат агента проверялся так же.
  - AC:
    - MCP `submit_result` вызывает ту же логику и проверки, что `POST /tasks/{id}/proposals`.
    - Повтор с тем же `idempotency_key` возвращает прежнее предложение, дубль не создаётся.

### Проверка

- 🟢 Как проверяющий, я хочу видеть предложение результата вместе с критериями задания и выполненными проверками, чтобы оценить его по существу.
  - AC:
    - В карточке задачи показаны все версии: ссылки, статусы критериев, проверки, ограничения, прежние проверки.
    - Форма проверки показывает критерии задания с ключами.

- 🟢 Как проверяющий, я хочу вынести вердикт — принято, на доработку или отклонено — с основаниями по каждому обязательному критерию, чтобы формальная отметка без основания не закрывала работу.
  - AC:
    - Основание обязательно для любого вердикта.
    - «Принято» возможно, только если все обязательные критерии задания отмечены выполненными (`CRITERIA_NOT_MET` иначе).
    - Проверка неизменна; вердикт становится статусом версии и определяет состояние результата задачи.

- 🟢 Как руководитель, я хочу, чтобы автор предложения не мог проверить его сам той же учётной записью, чтобы проверка была независимой.
  - AC:
    - Проверяет только участник с профилем проверяющего; автор результата и исполнитель задачи получают `SELF_REVIEW`, участник без профиля — `NOT_REVIEWER`.
    - Если задаче назначен проверяющий, проверить может только он (`NOT_DESIGNATED_REVIEWER`).
    - Форма проверки не показывается тем, кто не может проверять.

- 🟢 Как исполнитель, я хочу получить замечания проверки и подать новую версию, чтобы довести работу до принятого результата.
  - AC:
    - Автор результата получает уведомление о вердикте.
    - После «на доработку» исполнитель подаёт новую версию, и она требует новой проверки.

- 🟢 Как руководитель, я хочу видеть историю всех версий предложения и всех проверок, чтобы понимать, как задача пришла к результату.
  - AC:
    - Версии и проверки не удаляются; вкладка History показывает события подачи и проверки с авторами и временем.

### Состояния и видимость

- 🟢 Как руководитель, я хочу видеть раздельно «работа выполнена», «локально проверена», «поставка предложена» и «получатель принял», чтобы TaskTrack не выдавал собственную проверку за приёмку другим проектом.
  - AC:
    - Поставку можно предложить только после принятого результата (`RESULT_NOT_ACCEPTED` иначе).
    - Приёмку получателем записывает менеджер как полученный факт с автором, датой и источником; новая поставка сбрасывает прежнюю приёмку.
    - Тип задачи с обязательной проверкой переходит в финальный статус только после вердикта «принято» или «отклонено» (`RESULT_NOT_REVIEWED`).

- 🟢 Как проверяющий, я хочу видеть очередь проверки — результаты, ожидающие меня, — чтобы работа не застревала после выполнения.
  - AC:
    - Очередь на дашборде и в `GET /review-queue` содержит только версии, которые пользователь вправе проверить сейчас.

- 🟢 Как руководитель, я хочу, чтобы старые комментарии с меткой `solution` были перенесены как «историческое, формально не проверено», чтобы они не считались проверенным результатом.
  - AC:
    - Миграция создаёт по такому комментарию предложение со статусом «Historical», комментарий остаётся обсуждением.
    - Метка `solution` на новых комментариях ничего не меняет в задаче.

## U. Задание, сессии, контроль

- 🟢 Как руководитель, я хочу оформить задание — цель, ожидаемый результат, критерии, входы, ограничения, специализация — и выпустить неизменяемую версию, чтобы исполнитель и проверяющий работали по одному тексту.
  - AC:
    - Черновик редактирует автор задачи или менеджер; выпуск проверяет полноту (цель, результат, специализация, хотя бы один критерий) — неполное остаётся черновиком.
    - Выпущенная версия неизменна, у неё номер и digest; критерии получают ключи `c1`, `c2`…
    - Изменение черновика после выпуска видно как «Changed since issue»; выпуск без изменений отклоняется.

- 🟢 Как консольный агент, я хочу получить закреплённую копию задания (JSON/YAML) с ID, версией и digest, чтобы работать по точной версии.
  - AC:
    - `GET /work-packages/{id}/export` и MCP `get_work_package` отдают id, версию, digest и содержимое; без выпущенной версии агент видит, что задача не готова.

- 🟢 Как исполнитель (человек или агент), я хочу открыть сессию исполнения и сохранять контрольные точки, чтобы после сбоя продолжить с последней точки, а другой процесс не взял ту же работу.
  - AC:
    - Активная сессия исполнения на задаче одна; вторая попытка, даже под той же учётной записью, получает `SESSION_ACTIVE` с данными держателя.
    - Сессия закрепляет версию задания; изменения с `X-Task-Session` пишутся в журнал с сессией, результат получает её провенанс.
    - Сессия не истекает по времени; освободить её может владелец или менеджер с указанием причины.

- 🟢 Как руководитель, я хочу видеть открытую работу проекта с причинами ожидания, чтобы быстро найти необеспеченную работу, очередь проверки и зависшие сессии.
  - AC:
    - Страница Control показывает по каждой открытой задаче причины: нет задания, задание изменено, нет исполнителя, блокировка, ждёт проверки, на доработке, сессия молчит > 24 ч, ждёт получателя, результат не проверен.
    - Сводка по причинам и специализациям; фильтры по причине и специализации.

- 🟡 Как руководитель, я хочу видеть основание задачи (требование, риск, решение, регламент…) и актуальность её входов, чтобы работа со старым входом не выглядела готовой. — _После контракта внешних систем (FR-003, TT-10/11)._

## Отменено ADR-016

- 🔴 Как менеджер, я хочу назначить нескольких исполнителей с независимыми воркфлоу на одну задачу. — Параллельная работа выражается подзадачами.
- 🔴 Как decision-maker, я хочу выбрать итог среди Solution нескольких исполнителей по DecisionCriteria. — Заменено проверкой каждого предложения результата.
