# 09. MVP: сценарии и приоритизация

Исследовательская цель: прогнать 2–3 реальных проекта через трекер, собрать обратную связь. Масштаб небольшой, сроки сжатые — поэтому приоритет на ядро, а не на полноту.

> Исходная гипотеза — мульти-исполнители + Decision Process — отменена [ADR-016](./decisions/ADR-016-responsible-review-model.md) (2026-09-29). Ядро продукта теперь — предложение результата и независимая проверка (сценарии S2–S3 ниже, реализация — пакет C [FR-003](./feature-requests/FR-003-portfolio-execution.md)).

---

## Ключевые MVP-сценарии

### S1. Классический флоу (один исполнитель)
Менеджер создаёт проект → создаёт задачу → назначает одного исполнителя → исполнитель проводит задачу через воркфлоу → переводит в финальный статус.

Зачем: базовый юзабилити-контроль. Если это работает плохо — дальше не идём.

### S2. Предложение результата и независимая проверка 🟡
Руководитель формирует задачу с критериями → исполнитель ведёт её по воркфлоу → подаёт предложение результата (ссылки на PR / коммит, выполненные критерии и проверки) → проверяющий, не автор, проверяет его по критериям → принимает → задача выполнена.

Зачем: ядро продукта после ADR-016. Проверяем, что готовность подтверждается проверкой, а не отметкой.

### S3. Цикл доработки 🟡
Проверяющий возвращает предложение на доработку с замечаниями → исполнитель подаёт новую версию → новая проверка → принято. Прежние проверки остаются в истории.

Зачем: доработка — ожидаемый путь, не исключение. Должен быть первоклассным.

### S4. Видимость проекта
Администратор создаёт проект с уровнем `restricted` → добавляет конкретных пользователей / группу → остальные пользователи инстанса проект не видят.

Зачем: нужна хотя бы базовая изоляция для реальных проектов.

### S5. Связь между проектами
Менеджер устанавливает связь `related` между двумя проектами → пользователи видят её в карточке проекта → устанавливает связь между задачами из разных проектов (при наличии прав в обоих).

Зачем: проверяем, нужна ли эта механика на практике и в каком виде.

## Приоритизация user stories

Легенда: 🟢 MVP / 🟡 v2 / 🔴 не делаем в обозримой перспективе / ✏️ переформулировать

### A. Аутентификация и пространство пользователя
- 🟢 Регистрация по email + пароль
- 🟢 Вход через Google OAuth
- 🟡 SSO / SAML
- 🟢 Восстановление пароля
- 🟢 Дашборд «мои задачи»
- 🟢 Настройки уведомлений (базовые)
- 🟢 Профиль: имя, аватар, часовой пояс

### B. Проекты и пространства
- 🟢 Создать проект (название, ключ, описание, владелец)

- 🟢 Настроить воркфлоу проекта

- 🟢 Прикрепить файлы
- 🟢 Due date и оценка трудозатрат
- 🟢 Связи между задачами (блокирует, дубликат, related)
- 🟢 Редактировать задачу
- 🟢 Soft-delete задачи
- 🟡 Клонировать задачу

### D. Иерархия: эпики, подзадачи
- 🟡 Эпики
- 🟡 Подзадачи

### T. Результат и проверка
_(ADR-016; реализация — пакет C FR-003, TT-14–17)_
- 🟡 Подать предложение результата: ссылки на PR / коммит / релиз, выполненные критерии и проверки, ограничения
- 🟡 Подать новую версию предложения (прежняя неизменна)
- 🟡 Проверить предложение: вердикт (принято / на доработку / отклонено), критерии, основания
- 🟡 Запрет проверять собственный результат той же учётной записью
- 🟡 Новая версия требует новой проверки; история проверок сохраняется
- 🟡 Состояния «выполнено», «локально проверено», «поставка предложена», «получатель принял» — раздельно, со ссылками
- 🟡 Очередь проверки для руководителя
- 🟡 Перенос старых комментариев `solution` как «историческое, формально не проверено»
- 🔴 Несколько Solution от разных исполнителей и выбор Decision среди них — отменено ADR-016
- 🔴 DecisionCriteria, слепой режим, SLA и аналитика Decision Process — отменено ADR-016
