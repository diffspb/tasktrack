# Глоссарий

Единый словарь терминов проекта. **Все остальные документы должны использовать термины отсюда.** Если в обсуждении возник синоним — он попадает либо в столбец «синонимы (не использовать)», либо становится новым отдельным термином.

Каждая запись содержит:
- **EN** — каноническое имя для кода и API
- **RU** — единственное допустимое название в документации и UI
- **Определение** — что это
- **Не путать с** — близкие, но разные сущности
- **Синонимы (не использовать)** — слова, которые встречались в черновиках, но больше не должны употребляться

**Маркер состояния** показывает, есть ли термин в текущем коде (`main`, сверено 2026-07-27). Термин без маркера реализован:

| Маркер | Значение |
|--------|----------|
| 🟡 не реализован | Термин продуктовый, сущности в коде пока нет |
| 🔴 удалён | Был в коде, удалён осознанно; возврат не планируется без нового решения |
| ⛔ отменён | Продуктовое понятие, от которого отказались ([ADR-016](./decisions/ADR-016-responsible-review-model.md)); в новых документах не употреблять |

## Сущности и роли

### User / Пользователь
Человек с учётной записью в системе. Принадлежит инстансу. В разных проектах может иметь разные роли.

### ServiceAccount / Служебная учётная запись
Учётная запись агента или интеграции (`User.is_service`). Не входит через Keycloak, аутентифицируется ключом API. Права получает как пользователь — через членство в проекте и роль. Действия записываются от её имени. См. [ADR-017](./decisions/ADR-017-service-accounts-api-keys.md).
**Синонимы (не использовать):** «бот», «агент-пользователь» (для записи в БД; «агент» — это программа, которая ей пользуется).

### ApiKey / Ключ API
Секрет служебной учётной записи вида `tt_…` для REST и MCP. Хранится только хеш; токен показывается один раз. Отзывается и ротируется без перезапуска сервиса.
**Не путать с:** `MCP_AGENTS` — устаревший способ задать ключи агентов в окружении.

### Group / Группа пользователей 🟡 не реализован
Именованное объединение пользователей. Используется при настройке прав и видимости.

### Project / Проект
Контейнер для задач. У проекта есть владелец, участники, роли, типы задач, воркфлоу, статусы и представления. Между проектами могут быть **связи** (см. ProjectLink).

### ProjectLink / Связь между проектами 🟡 не реализован
Отношение между двумя проектами. Конкретный набор типов связей определяется отдельно (см. задачу 2.2 в `08-pre-design-tasks.md`).

### Task / Задача
Атомарная единица работы. Имеет заголовок, описание, тип, приоритет, проект, исполнителя, статус, даты. Может быть подзадачей или частью эпика.

### Epic / Эпик
Крупная инициатива, объединяющая несколько задач. Имеет агрегированный прогресс по входящим в него задачам.

### Subtask / Подзадача
Задача, у которой есть родительская задача. Прогресс подзадач влияет на прогресс родителя.

### TaskType / Тип задачи
Справочник типов: системные (`task`, `bug`, `story`, `epic`, `decision`, `project_id = NULL`) и проектные кастомные. Определяет иконку, цвет и — через `ProjectTaskTypeConfig` — воркфлоу для новых задач этого типа в проекте.

### Workflow / Воркфлоу
Граф статусов и допустимых переходов между ними для определённого типа задачи. Привязан к проекту; `project_id = NULL` — системный воркфлоу, доступный всем проектам.

### Status / Статус
Положение задачи (или Assignment) в воркфлоу. Например: «Новая», «В работе», «Готово».
**Не путать с:** Resolution.

### Transition / Переход
Допустимое изменение статуса с условиями и правами. Например: переход «В работе → Готово» только для роли `manager` (поле `required_role`; `NULL` — переход доступен всем участникам проекта).

### Resolution / Резолюция 🔴 удалён
Категория результата задачи: Done / Won't Fix / Duplicate / Cannot Reproduce / Out of Scope и т.д. В исходной модели назначалась **per Assignment** (отменено ADR-016).
Таблица, сервис и эндпоинты удалены в `8b7f59f` (2026-05-06, [ADR-015](./decisions/ADR-015-resolution-removal.md)) как преждевременная мера: переход в финальный статус резолюции не требует. Истории сняты с MVP в 🟡 v2 (2026-07-28); возврат — только через новый ADR.
**Не путать с:** Status, Review.

### Assignment / Назначение ⛔ отменён
Запись «пользователь работает над задачей» с персональным статусом; на задаче их могло быть несколько. Удалена из кода MVP-упрощением ([ADR-014](./decisions/ADR-014-mvp-simplification-assignment.md)), от восстановления отказались ([ADR-016](./decisions/ADR-016-responsible-review-model.md)). У задачи один исполнитель — `Task.assignee_id`; параллельная работа — через подзадачи.

### AssigneeRole / Роль исполнителя в задаче ⛔ отменён
Роль исполнителя внутри задачи (lead / reviewer / consultant) в модели нескольких исполнителей. Отменена вместе с Assignment. Проверка результата — отдельная роль **Reviewer / Проверяющий**, не роль исполнителя.

## Результат и проверка

> ⚠️ Слово «решение» в русском многозначно и в документации само по себе не используется. Результат работы — **предложение результата**, оценка другим человеком — **проверка**.

> Суррогат прежней модели снят ([ADR-021](./decisions/ADR-021-result-proposal-review.md)): метка комментария `solution` ничего не значит, старые такие комментарии перенесены в предложения результата со статусом «историческое, формально не проверено».

### WorkPackage / Задание
Что нужно сделать по задаче: цель, ожидаемый результат, критерии приёмки (с ключами `c1`, `c2`…), входы, ограничения, специализация. Редактируется черновиком; выпущенная **версия задания** неизменна и имеет digest. Неполное задание остаётся черновиком — задача не готова к исполнению. См. [ADR-020](./decisions/ADR-020-work-package.md).
**Не путать с:** описанием задачи (`description`) — это свободный текст.
**Синонимы (не использовать):** «ТЗ», «пакет» без уточнения.

### TaskSession / Сессия исполнения
Конкретный запуск работы над задачей: кто, на какой машине, по какой версии задания, с какими контрольными точками. У задачи не больше одной активной сессии исполнения; сессия заканчивается только явно — завершением или освобождением с причиной. См. [ADR-022](./decisions/ADR-022-task-sessions.md).
**Не путать с:** сессией входа пользователя (Keycloak).

### Process type / Тип-процесс
Системный тип задачи со своим воркфлоу и обязательной проверкой результата: **исполнение** (`execution`), **исследование** (`research`, итог — вывод, в том числе «не применять»), **миграция** (`migration`). См. [ADR-023](./decisions/ADR-023-process-types.md).

### ResultProposal / Предложение результата
Структурированный результат, который исполнитель предъявляет по задаче: ссылки на PR / коммит / релиз, выполненные критерии и проверки, ограничения, происхождение; относится к конкретной версии задания. Неизменяем после подачи — исправление подаётся новой версией. На задаче может быть несколько предложений.
**Не путать с:** Comment — комментарий остаётся обсуждением и результатом не является.
**Синонимы (не использовать):** «решение», «Solution», «сдача».

### Review / Проверка результата
Отдельная запись о проверке конкретной версии предложения результата: кто проверил, по каким критериям, вердикт (принято / на доработку / отказ) и основания. Автор предложения не проверяет его сам той же учётной записью; новая версия предложения требует новой проверки, прежние проверки остаются в истории.
**Не путать с:** приёмкой поставки получателем в другом проекте — её фиксирует офис, TaskTrack лишь отображает факт.
**Синонимы (не использовать):** «Decision», «вердикт» как название сущности, «апрув».

### Reviewer / Проверяющий
Участник проекта с **профилем проверяющего** (`ProjectMember.is_reviewer`, выдаёт менеджер). Не может проверять свой результат и задачу, где он исполнитель. Роль в проекте профиль не заменяет. Задаче можно назначить конкретного проверяющего. См. [ADR-021](./decisions/ADR-021-result-proposal-review.md).

### Solution / Поданное решение ⛔ отменён
Вариант, который исполнитель подавал в Decision Process. Заменён предложением результата ([ADR-016](./decisions/ADR-016-responsible-review-model.md), [ADR-021](./decisions/ADR-021-result-proposal-review.md)).

### Decision / Итоговое решение ⛔ отменён
Выбор decision-maker'а среди нескольких Solution. Заменён проверкой результата.

### DecisionCriteria / Критерии принятия решения ⛔ отменён
Критерии выбора Solution. Критерии теперь — часть задания и предложения результата (FR-003, TT-09 / TT-14).

### DecisionMaker / Лицо, принимающее решение ⛔ отменён
Лицо, выносившее Decision. Заменено проверяющим. Тип задачи `decision` остался: такая задача ждёт, пока каждая подзадача подаст предложение результата.

### Decision Process / Процесс принятия решения ⛔ отменён
Этап задачи с несколькими Solution и выбором Decision — бывшая ключевая механика продукта. Отменён [ADR-016](./decisions/ADR-016-responsible-review-model.md).

### Submission / Подача решения ⛔ отменён
Подача Solution. Заменяется подачей предложения результата.

### Revision / Доработка
Возврат результата исполнителю с замечаниями. В новой модели — вердикт проверки «на доработку»; исполнитель подаёт новую версию предложения результата.

## Что было «исполнитель»

В черновиках встречались слова **«исполнитель»**, **«assignee»**, **«соисполнитель»**. Канонизируем:

| Контекст | Используем |
|----------|------------|
| Человек (или служебная учётная запись), выполняющий задачу | **исполнитель** (англ. assignee, поле `Task.assignee_id`) — один на задачу |
| Человек, проверяющий результат | **проверяющий** (англ. reviewer) |

Слова **«соисполнитель»** и **«исполнители задачи»** (во множественном числе про одну задачу) **не используем**: у задачи один исполнитель ([ADR-016](./decisions/ADR-016-responsible-review-model.md)).
