# ADR-023: Типы-процессы (исполнение, исследование, миграция) и валидация метаданных

**Статус:** Принято — решение принято при автономной реализации FR-003 (TT-13), подлежит ревью владельцем продукта  
**Дата:** 2026-09-30

## Контекст

[FR-003](../feature-requests/FR-003-portfolio-execution.md), TT-13: «согласованные процессы исполнения, проверки, исследования и миграции; валидация метаданных по схеме типа. Переход требует нужных полей и полномочий. Исследование может завершиться выводом «не применять», а не фиктивной реализацией». В модели уже было поле `TaskType.meta_schema`, но оно нигде не проверялось.

Главный риск — сломать текущую работу: если потребовать проверку результата от обычных задач, существующие проекты перестанут закрывать задачи.

## Решение

- **Схема метаданных:** `TaskType.meta_schema` (JSON Schema 2020-12) проверяется при создании задачи и при изменении `meta`; ошибка — `422 META_INVALID` с путями полей.
- **Обязательные поля перехода:** `Transition.required_fields` — ключи `meta`, которые должны быть непустыми для входа в целевой статус (`400 TRANSITION_FIELDS_REQUIRED` со списком). Правятся `PATCH /transitions/{id}` вместе с `required_role`; экспорт и импорт проекта их переносят.
- **Системные процессы** (создаются идемпотентно при старте приложения, `ensure_process_types`), все с `requires_review` (ADR-021):
  - `execution` «Исполнение»: To Do → In Progress → On Review → Done;
  - `research` «Исследование»: Open → Investigating → Concluded; для Concluded нужны `conclusion` ∈ {`apply`, `do_not_apply`, `inconclusive`} и `findings`. Вывод «не применять», прошедший проверку, — законное завершение;
  - `migration` «Миграция»: Planned → Migrating → Verified; нужны `source_system` и `source_ref`.
- «Процесс проверки» — это сущности предложения результата и проверки (ADR-021), а не отдельный тип задачи.
- Задачи-процессы по умолчанию идут по воркфлоу своего процесса, а не по воркфлоу проекта: процесс и есть воркфлоу. Настройка типа в проекте (`ProjectTaskTypeConfig`) по-прежнему имеет приоритет.
- Существующие типы (`task`, `bug`, `story`, `epic`, `decision`) не меняются: проверка результата для них не обязательна.

## Последствия

- Статусы процессов не сопоставлены колонкам Kanban-доски проекта — такие задачи видны в списке, бэклоге и на странице Control, но не на доске, пока колонки не настроены (`ux-debt.md`).
- Обязательную проверку результата получают новые задачи типов-процессов; переводить на неё существующие задачи — решение проекта (смена типа или настройка).
- Типизированные основания задачи (TT-10) и правила готовности (TT-11) добавятся к процессам после контракта внешних систем.
