# ADR-016: Один ответственный, предложения результата и независимая проверка вместо мульти-исполнителей

**Статус:** На рассмотрении — уточняет [ADR-001](./ADR-001-decision-process.md) и план восстановления из [ADR-014](./ADR-014-mvp-simplification-assignment.md)  
**Дата:** 2026-09-29  
**Владелец:** владелец продукта; решение принимается до начала пакетов B–D [FR-003](../feature-requests/FR-003-portfolio-execution.md)

## Контекст

[ADR-001](./ADR-001-decision-process.md) сделал ключевой фичей продукта несколько исполнителей с независимыми воркфлоу и Decision Process (`Assignment` → `Solution` → `TaskDecision`). [ADR-014](./ADR-014-mvp-simplification-assignment.md) откатил эту модель до одного `Task.assignee_id` с суррогатом Solution в комментарии и зафиксировал восстановление как долг (`docs/tech-debt.md`).

[FR-003](../feature-requests/FR-003-portfolio-execution.md) ставит TaskTrack в портфель, где работу выполняют консольные агенты и люди, а результат должен быть проверен независимо. Он прямо предлагает не восстанавливать модель нескольких Assignment/Solution: «первой версии достаточно одного ответственного, нескольких предложений результата и отдельной проверки каждого».

Варианты:
1. Восстановить модель ADR-001 (мульти-исполнители + Decision Process), как записано в долге.
2. Принять модель FR-003: один ответственный на задачу, несколько структурированных предложений результата, отдельная запись проверки каждого предложения независимым проверяющим.
3. Совместить: модель FR-003 сейчас, мульти-исполнителей — поверх неё позже.

## Решение (предлагаемое)

Вариант 2 с оставленной дверью в вариант 3:

- У задачи один ответственный (`Task.assignee_id`). Параллельность — через подзадачи, а не через `Assignment`.
- Результат — отдельная сущность (рабочее имя `ResultProposal`, TT-14): ссылки на PR/коммит/релиз, критерии, выполненные проверки, ограничения, версия пакета работы. Предложений на задачу может быть несколько.
- Проверка — отдельная сущность (рабочее имя `Review`, TT-15): кто, какую версию предложения, по каким критериям, вердикт, основания. Автор не проверяет собственный результат той же учётной записью; новая версия предложения требует новой проверки.
- Суррогат `Comment.labels=["solution"]` выводится из употребления; существующие помечаются «историческое, формально не проверено».
- Термины `Solution`/`Decision` в глоссарии не переиспользуются для новых сущностей, пока не решено, заменяют ли они их (см. последствия).

## Последствия

- При принятии: пункты «Мульти-исполнители и Assignment» и «Decision Process (Solution / TaskDecision)» в `docs/tech-debt.md` снимаются как долг; `04-multi-assignee.md`, `07-decision-process.md`, `stories/decision-process.md` помечаются историческими или переписываются; `README.md` и `00-context.md` меняют формулировку ключевой фичи.
- Нужно решение по терминам в `glossary.md`: остаётся ли «Solution» названием предложения результата, а «Decision» — проверки, или вводятся новые термины.
- ADR-008 (триггер `awaiting_decision`) окончательно становится неприменимым.
- Модель проще восстановления ADR-001: нет двухуровневых статусов, от которых отказались в ADR-014.
- Вариант 3 остаётся открытым: `ResultProposal` не привязан к единственному исполнителю жёстко (хранит автора), поэтому мульти-исполнители можно вернуть без миграции предложений.
- Дефекты пакета A FR-003 (TT-01–03) от этого решения не зависят и исправляются независимо.
