# ADR-018: Аудит-лог и журнал событий — одна таблица, запись в транзакции изменения, курсор без пропусков

**Статус:** Принято — решение принято при автономной реализации FR-003 (TT-06), подлежит ревью владельцем продукта  
**Дата:** 2026-09-29

## Контекст

[FR-003](../feature-requests/FR-003-portfolio-execution.md), TT-06: «сохраняемый аудит и журнал событий, записываемые вместе с изменением; получение событий с восстановлением. После перезапуска доступны причина, автор и состояние до/после. Повтор события безопасен. Конкурентная фиксация транзакций не приводит к пропуску за курсором».

До этого изменения в коде были только SSE-уведомления через `EventBus` в памяти процесса: они теряются при перезапуске, при медленном клиенте и между процессами. Истории изменений задачи не было.

Варианты:
1. Отдельные таблицы для аудита (людям) и для журнала событий (сервисам).
2. Одна append-only таблица: аудит — это чтение журнала с фильтром.
3. Внешний брокер (Kafka / NATS) с outbox.

Отдельный вопрос — курсор. Автоинкрементный `id` выдаётся при вставке, а транзакции фиксируются в другом порядке: читатель может увидеть `id=11`, сдвинуть курсор и навсегда пропустить `id=10`, зафиксированный позже.

## Решение

Вариант 2, без брокера: масштаб — внутренний инструмент, одна БД.

- **Таблица `audit_events`** (`AuditEvent`): `id`, `xid` (id транзакции-писателя), `occurred_at`, `actor_id`, `project_id` (NULL — системные события), `task_id` (для истории задачи: сама задача, её комментарии и связи), `entity_type`, `entity_id`, `action`, `reason`, `before`, `after`. Внешних ключей нет: запись переживает описываемые строки.
- **Запись** — `audit_service.record()` до `commit` сервиса, в той же транзакции. Откат команды откатывает и событие. Для правок `before`/`after` содержат только изменённые поля; для создания — полный снимок в `after`, для удаления — в `before`. Причина — заголовок `X-Change-Reason` (UTF-8 в percent-encoding, до 500 символов).
- **Курсор** — пара `(xid, id)`, строка `"<xid>.<id>"`. Отдаются только события транзакций с `xid < pg_snapshot_xmin(pg_current_snapshot())` (плюс собственной транзакции читателя). Любая транзакция, которая ещё может добавить событие, имеет `xid ≥ xmin`, поэтому её событие не может оказаться позади уже выданного курсора. Цена — событие становится видно читателю после завершения всех более старых транзакций (обычно миллисекунды).
- **Повтор безопасен:** чтение с тем же курсором возвращает те же события; у события стабильный `id` — потребитель дедуплицирует по нему.
- **Чтение:** `GET /projects/{id}/audit-log` — всем, кто видит проект; `GET /tasks/{id}/history` — всем, кто видит задачу; `GET /admin/audit-log` (системные события: служебные учётные записи, ключи API) — только суперпользователю.
- SSE (`/projects/{id}/events`) остаётся подсказкой для обновления интерфейса и не заменяет журнал.

## Последствия

- Журнал проекта читают все, кто видит проект, а не только администратор, как в `13-permissions.md`: он раскрывает лишь данные, которые читатель и так видит. Системный журнал — только суперпользователю. Матрица прав обновлена.
- Размечены: задачи (создание, правка, переход, удаление), комментарии, связи задач, проект (создание, правка, архивация), участники, служебные учётные записи и ключи API. Не размечены: воркфлоу, статусы, переходы, представления и колонки борды, Гант, импорт проекта — `docs/tech-debt.md`.
- Таблица растёт без ограничения; политика хранения не задана (`10-nfr.md`: «нет авто-удаления»).
- Долгая транзакция задерживает выдачу всех более новых событий до своего завершения — ожидаемое свойство горизонта.
- Основа для TT-04 (идемпотентность) и для будущей записи Decision и проверок (TT-15): новые сущности добавляют свои `entity_type`.
