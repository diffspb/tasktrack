# ADR-021: Предложение результата, проверка и профиль проверяющего

**Статус:** Принято — решение принято при автономной реализации FR-003 (TT-14–17) по [ADR-016](./ADR-016-responsible-review-model.md); выбор модели проверяющего подлежит ревью владельцем продукта  
**Дата:** 2026-09-30

## Контекст

ADR-016 сделал главной механикой продукта независимую проверку результата. Нужно определить: как устроен результат, кто может проверять, что значит «принято», как отличить локальную проверку от приёмки поставки другим проектом, и что делать с суррогатом — комментарием с меткой `solution`.

Вопрос «кто проверяющий» владелец не решил явно. Варианты: любой участник кроме автора; менеджер и администратор; отдельный профиль проверяющего.

## Решение

- **ResultProposal** — результат, который подаёт **исполнитель задачи**: сводка, ссылки (`pr`/`commit`/`release`/`build`/`document`/`other`), статусы критериев задания, выполненные проверки, ограничения, происхождение (сессия, машина). Относится к версии задания. Содержимое неизменно; исправление — новая версия с `supersedes_id`, прежняя становится `superseded`. До проверки автор может отозвать версию.
- **Review** — неизменяемая запись проверки одной версии: проверяющий, вердикт `accepted` / `changes_requested` / `rejected`, оценки критериев, **обязательное основание**. `accepted` возможен, только если все обязательные критерии задания отмечены `met` (`422 CRITERIA_NOT_MET`). Новая версия требует новой проверки; прежние остаются в истории.
- **Профиль проверяющего** — флаг `ProjectMember.is_reviewer`, выдаёт менеджер. Роль в проекте его не заменяет: менеджер без флага не проверяет. Проверять нельзя собственный результат и задачу, где ты исполнитель (`SELF_REVIEW`). Менеджер может назначить задаче конкретного проверяющего (`Task.reviewer_id`, только с профилем) — тогда проверяет только он.
- **Состояние результата** `Task.result_state` вычисляется из версий: `accepted` › `proposed` › `changes_requested` › `rejected` › `historical` › `none`.
- **Поставка и приёмка** (TT-17) — отдельные факты: после `accepted` исполнитель или менеджер предлагает поставку (`Task.delivery`), менеджер записывает приёмку получателем как **полученный факт** с автором и датой (`Task.recipient_acceptance`). TaskTrack не принимает поставку за получателя.
- **Закрытие.** Тип задачи с `requires_review` (процессы, ADR-023) переходит в финальный статус только при `accepted` или `rejected` (аргументированный отказ): иначе `400 RESULT_NOT_REVIEWED`. Для остальных типов поведение не меняется.
- **Суррогат снят.** Метка `solution` — обычная метка комментария. Миграция перенесла живые `solution`-комментарии в предложения со статусом `historical` («историческое, формально не проверено»). Задача типа `decision` ждёт, пока у каждой подзадачи появится предложение результата.
- Проверяющий видит очередь: `GET /review-queue`, карточка «Awaiting my review» на дашборде, MCP `list_review_queue`.

## Последствия

- Готовность задачи подтверждается записью проверки с основанием; ни комментарий, ни повтор команды её не создают.
- Для работы механики менеджер должен выдать кому-то профиль проверяющего. Для небольших команд это лишний шаг, но так проверка остаётся явным полномочием, а не побочным эффектом роли.
- Несколько предложений на задаче допустимы; принятие любого делает результат задачи принятым. Выбор «лучшего из нескольких» (прежний Decision) не реализуется.
