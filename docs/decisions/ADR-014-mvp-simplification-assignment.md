# ADR-014: MVP-упрощение модели задачи — отказ от Assignment и Decision Process

**Статус:** Принято  
**Дата решения:** 2026-05-02 (коммит `40caac4`)  
**Дата записи ADR:** 2026-07-27 — решение принималось в коде, в ADR-каталоге зафиксировано задним числом при сверке документации с реализацией.

## Контекст

К концу этапа 7 в коде существовали `Assignment`, `Solution`, `DecisionCriteria`, `TaskDecision` и поле `Task.global_status`. Ключевая фича продукта — несколько исполнителей с независимыми воркфлоу и Decision Process — была реализована на уровне API и UI (теги `impl-phase-6`, `s23-complete`).

Проблема: базовый флоу задачи (создать → назначить → провести по воркфлоу → закрыть) при этом оставался неудобным. Каждое обращение к статусу задачи шло через Assignment, `global_status` пересчитывался при любом изменении, а на борде задача не имела собственного статуса. Отладка простейших сценариев требовала держать в голове два уровня статусов. Исследовательский запуск планировался на 2–3 реальных проекта, где мульти-исполнительские задачи — скорее исключение.

Варианты:
1. Оставить как есть и дорабатывать UX поверх двухуровневой модели.
2. Свернуть модель до одного исполнителя, вернуть мульти-исполнителей после того, как базовый флоу устоится.

## Решение

Принят вариант 2. Удалены:

- таблицы `Assignment`, `Solution`, `DecisionCriteria`, `TaskDecision`;
- поле `Task.global_status`;
- роутеры `api/v1/solutions.py`, `api/v1/decisions.py`.

Введено взамен:

- `Task.assignee_id` — один исполнитель, FK на `users`, nullable;
- `Task.current_status_id` переехал с Assignment на Task;
- `Task.parent_task_id` — самореференс, через него выражаются подзадачи и «части» decision-задачи;
- `Comment` как первоклассная сущность с `labels`; Solution в MVP — комментарий с `labels=["solution"]`, ссылка хранится в `Task.meta.solution_comment_id`;
- `TaskType` — справочник типов, включая системный тип `decision`.

Блокировка перехода decision-задачи в финальный статус, пока не закрыты её части, сохранена в `task_service._check_decision_task_unblocked`.

## Последствия

- Базовый флоу (S1) стал прямым: задача имеет один статус, борда работает без пересчёта агрегата.
- **Ключевая дифференцирующая фича продукта в коде отсутствует.** Этапы 6–7 остаются закрытыми по тегам, но их результат откатан — это зафиксировано в `docs/README.md`, `CLAUDE.md` и `18-implementation-plan.md`.
- Decision Process в MVP — суррогат на комментариях: у него нет явного контракта, состояний `draft → submitted → accepted / revision_requested` и защиты от конкурентной подачи. Клиент вынужден знать про `labels` и `meta`.
- `frontend/src/features/decision-process/` пуст.
- [ADR-008](./ADR-008-awaiting-decision-trigger.md) (триггер `awaiting_decision` по `Solution.submit`) в текущем коде неприменим — он описывает состояние, к которому предстоит вернуться.
- Восстановление описано в `docs/tech-debt.md`; целевая механика — в `07-decision-process.md` и `04-multi-assignee.md`. Возврат должен идти в порядке `Assignment` → `Solution` → `TaskDecision`, поскольку каждая следующая сущность зависит от предыдущей.
- Пока фича не восстановлена, продукт функционально равен обычному таск-трекеру — это ограничивает ценность исследовательского запуска и должно учитываться при формулировке вопросов к пилотным командам.
