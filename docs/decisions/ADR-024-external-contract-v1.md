## Контекст

Шесть пунктов [FR-003](../feature-requests/FR-003-portfolio-execution.md) ждали идентификаторов и правил внешних систем. Заказчик выпустил контракт: смысл данных и обязательное поведение заданы, названия операций, таблицы и схемы выбирает TaskTrack. Реальный API офиса, продукт требований и Office Job/Attempt не являются входом этапа — поддержка проверяется на ручном импорте и тестовом (учебном) поставщике.

## Решение

### Принятие версии

TaskTrack принимает версию 1.0 по хешу выше. Изменение смысла контракта принимается только новой версией с оценкой влияния; реализация ссылается на `tasktrack-external-v1` в каждом событии обмена (`contract_version`). Изменение закреплённой копии без нового ADR запрещено.

### Техническое отображение

| Понятие контракта | В TaskTrack |
|---|---|
| Реестр поставщиков | `ExternalProvider`: постоянный `key`, разрешённые пространства, виды фактов, способ получения (`manual` / `snapshot` / `adapter`), признак учебного. Ведёт суперпользователь. Адрес сервиса не входит в идентичность |
| Составная ссылка, идентичность | `ExternalObject`: `provider` + `namespace` + `type` + `ext_id` (уникально), `locator` отдельно |
| Редакция и закреплённый снимок | `ExternalRevision`: непрозрачная строка `revision`, точные байты оригинала и их SHA-256, время сведений, время регистрации, автор утверждения, зарегистрировавший пользователь, происхождение. Тот же объект и редакция с другими байтами — `409 INTEGRITY_CONFLICT`. Если у поставщика нет редакций — `revision = "sha256:<hex>"`. `latest` / `head` / `current` / названия веток отклоняются как незакреплённые |
| Текущая редакция | На `ExternalObject`: `current_revision` и `revision_state` (`current` / `pending_reconciliation`). Меняется только явным замещением (`supersedes`), подтверждением поставщика или полным снимком; поздняя старая редакция её не откатывает |
| Смена идентичности | `ExternalIdentityAlias`: явное соответствие старой идентичности объекту с причиной и автором |
| Факты | Редакции объектов видов `allocation`, `authorization`, `input_acceptance`, `recipient_acceptance`, `evidence`… с разобранными утверждениями (`claims`). Факт от поставщика, не уполномоченного на этот вид, сохраняется как **непроверенное сообщение** и не удовлетворяет готовности. Учебный факт не удовлетворяет готовности реального проекта. Отзыв — явная редакция со статусом `revoked` |
| Событие обмена | `ExternalEvent`: версия договора, поставщик, постоянный `event_id`, объект и редакция, время события и регистрации, хеш содержания, происхождение, итог. Повтор с тем же содержимым — подтверждение без мутации; другое содержимое — `409 EVENT_CONFLICT`; права проверяются и при повторе |
| Снимок для восстановления | `ExternalSnapshot`: поставщик, пространство, область (виды), полнота (`full` / `partial`), время сведений, позиции. Снимок авторитетно задаёт текущие редакции перечисленных объектов; отсутствие объекта ничего не удаляет |
| TT-08 связь проекта | `ProjectPortfolioLink`: режим портфельного управления, ссылка на проект офиса (уникальна в установке), основной репозиторий, закреплённая редакция регламента, признак учебного проекта. Без связи проект — самостоятельный, внешние проверки к нему не применяются |
| TT-10 основания | `TaskBasis`: объект, закреплённая редакция, роль (`cause` — причина работы, `input` — обязательный вход, `normative` — нормативное основание, `reference` — информационная ссылка, `grant` — выделение/разрешение), смысл связи, правило свежести. Выпуск WorkPackage закрепляет основания задачи в содержимом версии |
| TT-11 готовность | Вычисляемая проверка из пяти условий контракта с причинами, основаниями и датой сведений; применяется в портфельном режиме при захвате сессии исполнения и при переходе задачи из начального статуса (REST и MCP). Плюс `TaskBlocker` для зарегистрированных блокировок и `ImpactAssessment` для новой редакции обязательного основания |
| TT-19/20 предложения работы | `WorkProposal` с ключом (проект, этап, вид работы, идентичность основания без редакции, `work_scope_key`) и версиями `WorkProposalVersion` по редакциям основания; решение руководителя: создать задачу, связать, объединить, отложить, отклонить |
| TT-21 поставка и приёмка | `Delivery` → точная версия `ResultProposal` и `WorkPackage`; `RecipientAcceptance` → точная поставка, получатель, область использования, автор, дата, источник полномочия. Прежние поля `Task.delivery` / `recipient_acceptance` остаются сводкой; старые ручные записи переносятся как исторические без привязки |
| Вывод о соблюдении требования, проверки CI, релизы | Полученные факты вида `evidence` с `claims.kind` (`compliance_conclusion`, `ci_check`, `release`) и ссылками на точные редакции / коммиты; TaskTrack их показывает и не выводит из собственного `Done` |
| TaskSession ↔ Office Job/Attempt | Не реализуется: связь необязательна, пока диспетчера нет |

### Решения по местам, которые контракт оставляет исполнителю (предложены заказчику)

1. **Вывод о соблюдении требования не имеет своего вида** в перечне `type`. Используется `evidence` с `claims.kind = "compliance_conclusion"`. Предложение к v1.1: добавить вид `compliance_conclusion`.
2. **Получатель подтверждения входа** обозначается ссылкой на проект офиса из связи TT-08; для проекта без ссылки на офис допускается локальный ключ проекта TaskTrack (`tasktrack:<KEY>`).
3. **«Этап»** — строка, задаваемая проектом (например, `pilot`, `release-1`); сравнивается на точное равенство, словарь этапов контракт не задаёт.
4. **«Переход к исполнению»** — переход задачи из статуса категории `initial` в любой другой. Проверка готовности применяется к нему и к захвату сессии исполнения.
5. **Правило свежести** задаётся на основании: `pinned` (достаточно принятого закреплённого снимка) или `confirm_current` (нужно подтверждённое текущее состояние поставщика; неизвестное — блокирует). Разрешения (`grant`) всегда проверяются по сроку действия из их содержания.
6. **Учебный проект.** Связь проекта может быть помечена учебной — тогда учебные факты удовлетворяют его готовности; реальному проекту они не засчитываются никогда.

## Последствия

- Самостоятельные проекты работают как раньше; существующие задачи, задания, результаты, проверки и история не меняются. Миграция не создаёт оснований и не блокирует прежние задачи.
- Поддержка контракта испытывается на тестовом поставщике и ручном импорте (`backend/tests/test_external_contract.py`). **Подключение реальных поставщиков (офис, система требований, репозиторий) не выполнено**: нет адресов, ключей, реальных идентификаторов и выбранного продукта требований — это отдельный незавершённый объём FR-003.
