# ADR-017: Служебные учётные записи и ключи API вместо `MCP_AGENTS`

**Статус:** Принято — решение принято при автономной реализации FR-003 (TT-05), подлежит ревью владельцем продукта  
**Дата:** 2026-09-29  
**Заменяет:** схему аутентификации агентов из [ADR-010](./ADR-010-mcp-server.md) (раздел multi-agent auth); сам MCP-сервер из ADR-010 не меняется

## Контекст

[ADR-010](./ADR-010-mcp-server.md) аутентифицировал агентов по переменной `MCP_AGENTS=key:uuid,…`: ключи лежат в окружении открытым текстом, читаются один раз при старте и печатались в лог. Отозвать или сменить ключ можно только правкой окружения и перезапуском. REST такие ключи не принимает, поэтому агент с REST-клиентом и тот же агент через MCP проверяются по-разному. В dev-режиме (`MCP_AGENT_USER_ID` без `MCP_AGENTS`) MCP принимает вызовы вообще без ключа, и ничто не мешает включить этот режим на рабочей установке; то же с `AUTH_STUB=true`.

[FR-003](../feature-requests/FR-003-portfolio-execution.md), TT-05 требует: служебные учётные записи, ограниченные права, отзыв и ротацию без перезапуска, фактического автора в истории, одинаковые ограничения REST и MCP, отсутствие секретов в журналах и тестового обхода в рабочей установке.

Варианты:
1. Клиенты Keycloak (client credentials) для каждого агента.
2. Собственные ключи API в БД, привязанные к служебной учётной записи TaskTrack.

## Решение

Вариант 2. Keycloak остаётся для людей; агенту не нужен отдельный клиент в realm и выпуск JWT, а отзыв и ротация делаются внутри TaskTrack.

- **Служебная учётная запись** — `User` с `is_service = true`, `keycloak_id = "service:<uuid>"` (не совпадает ни с одним `sub` Keycloak). Войти через Keycloak нельзя.
- **Права** — как у людей, через членство в проектах и роль. Агент только для чтения — роль `viewer`. Отдельных «скоупов» у ключа нет: одна модель прав на всё.
- **Ключ API** (`ApiKey`) — токен `tt_<43 символа>` (256 бит). В БД — только SHA-256 и первые 10 символов для опознания; токен показывается один раз при выпуске или ротации. У ключа есть имя, необязательный срок, отметка отзыва и последнего использования.
- **Проверка** — одна функция `api_key_service.authenticate` для REST (`Authorization: Bearer`, до проверки JWT и заглушки) и MCP. Обращение к БД на каждом запросе: отзыв ключа, истечение срока и деактивация учётной записи действуют сразу.
- **Управление** — только суперпользователь: `/api/v1/admin/service-accounts`, `/api/v1/admin/api-keys/*`; на сервере без UI — `scripts/service_account.py`.
- **Рабочая установка** — образ задаёт `APP_ENV=production`; при нём приложение не стартует с `AUTH_STUB=true` или с MCP без ключа (`MCP_AGENT_USER_ID` без `MCP_AGENTS`).
- `MCP_AGENTS` продолжает работать ради существующих агентов, помечен устаревшим; ключи из него больше не пишутся в лог.

## Последствия

- Все действия агента записываются от его учётной записи (автор комментария, `reporter_id`) — «фактический автор». Полная история изменений — отдельно, TT-06.
- Проверка ключа — один индексный запрос на вызов; `last_used_at` обновляется не чаще раза в минуту.
- Хранится хеш без соли: токены случайные и длинные, перебор по хешу бессмыслен; медленный KDF не нужен.
- Интерфейса управления ключами во фронтенде нет — `docs/ux-debt.md`.
- Переход агентов с `MCP_AGENTS` на ключи — вручную: выпустить ключ, заменить заголовок в `.mcp.json`, удалить запись из `MCP_AGENTS`. После перехода всех — удалить поддержку `MCP_AGENTS` (новым ADR).
- Локальная разработка не затронута: без `APP_ENV` действует `dev`, `AUTH_STUB` и MCP без ключа работают как раньше.
