# ADR-022: Сессии исполнения — атомарное закрепление, контрольные точки, явное завершение

**Статус:** Принято — решение принято при автономной реализации FR-003 (TT-12), подлежит ревью владельцем продукта  
**Дата:** 2026-09-30

## Контекст

[FR-003](../feature-requests/FR-003-portfolio-execution.md), TT-12: «атомарное закрепление исполнителя и конкретной сессии; сохраняемая запись TaskSession, контрольные точки и возврат по явному решению. Два процесса, даже под одной учётной записью, не получают одно активное исполнение. Агентное изменение относится к действующей сессии и версии пакета. Потеря связи не освобождает GPU/стенд». План прямо говорит, что истечение времени не является подтверждением остановки.

## Решение

- **TaskSession**: задача, пользователь, закреплённая версия задания, роль (`executor` / `reviewer`), машина, рабочая папка, клиент, состояние (`active` / `completed` / `released`), последняя контрольная точка, итог, кто и почему завершил.
- **Одна активная сессия исполнения на задачу** — частичный уникальный индекс `(task_id) WHERE state='active' AND role='executor'` плюс блокировка строки задачи при открытии. Второй процесс получает `409 SESSION_ACTIVE` с данными держателя — даже под той же учётной записью. Сессию исполнения открывает только исполнитель задачи; сессия проверки — участник с профилем проверяющего.
- **Контрольные точки** (`SessionCheckpoint`) сохраняются в БД; восстановление после сбоя начинается с последней.
- **Завершение только явное:** владелец завершает (`complete`) или освобождает; менеджер освобождает чужую сессию с **обязательной причиной** (например, «процесс на gpu-1 проверен и остановлен»). Автоматического истечения нет; давность без контрольных точек показывается в представлении руководителя как `session_stale`.
- **Привязка изменений:** заголовок `X-Task-Session` (в MCP — параметр `session_id`) должен указывать на собственную активную сессию вызывающего (`409 SESSION_NOT_ACTIVE`). Такие изменения пишутся в журнал с `session_id`; предложение результата получает `session_id`, версию задания из сессии и провенанс (машина, папка, клиент).

## Последствия

- Потеря связи не освобождает задачу: повторный захват требует явного решения человека.
- При будущем диспетчере (Office Job/Attempt) сессия остаётся контекстом работы, а Job/Attempt — разрешением и фактом запуска; они будут связаны по ID. Это часть контракта внешних систем.
- Сессия не «держит» ресурс (GPU, стенд) в TaskTrack — учёт ресурсов принадлежит офису (TT-11).
